# Prototype standardの試遊優先モード

この文書は、操作感、画面、演出、ゲームバランスなどをプロジェクトオーナーが実際に触りながら決める変更に使う、consumer-localの暫定overrideである。新しいprofileは追加せず、`prototype-standard`の中で作業順だけを変える。

## 適用条件

- プロジェクトオーナーが短い周期で実際に操作し、方向を調整できる。
- 調整前に自動testや独立reviewを作り込むと、要求変更による作り直しが見込まれる。
- task開始時に試遊優先モードを使うこと、試遊へ出す最小経路、対象外を明示する。

認証、認可、PII、schema、migration、外部副作用、不可逆操作、データ損失のおそれがある変更には使わない。途中でこれらの境界が見つかった場合は探索を止め、通常のPrototype standardまたはDelivery-strictへ切り替える。

## 1. 探索と試遊

1. 既存Issue、仕様、実装経路を確認し、試遊できる最小変更だけを実装する。
2. 試遊依頼前に、利用可能なcompileまたはtypecheck、アプリ起動、変更した代表経路のsmokeを通す。データ損失や重要な既存契約に関わる対象検査は省略しない。
3. この段階では、新規unit / E2E、広い回帰test、正本文書の確定、独立した最終diff reviewを原則として後回しにする。観測を可能にする最小testや安全上必要なtestだけは追加できる。
4. 実装の場所、起動方法、確認してほしい項目、既知の未検証を示して、プロジェクトオーナーへ試遊を依頼する。
5. フィードバックで実装を変えた場合は、無効になったsmokeだけを再実行し、再度試遊を依頼する。

探索中は`Codex Agent checkpoint`の実装前planと最終diff reviewを後回しにできるが、writerを複数に増やさない。rootが適用条件と安全境界を確認し、一人のwriterだけが変更する。方向性確認後は、Terra Max planner/reviewerによる安定化planと最終diff reviewを通常どおり行う。

探索中の差分は方向性未確定であり、完了した作業とは扱わない。方向性確認前には原則としてstage・commitしない。

## 2. 方向性確認

プロジェクトオーナーの「この方向でよい」という回答を、最終受け入れではなく安定化開始の合図として扱う。GitHub taskがある場合は、遅くともPR作成前に、確認した方向と安定化で固定する範囲をIssueまたはPRへ記録する。

方向性が変わった場合、旧smoke、旧review、旧test結果は現在の完了根拠に再利用しない。

## 3. 安定化

方向性確認後に、通常のPrototype standardへ戻して次を行う。

1. 合意した範囲をrequirements / specsとtask Issueへ同期する。
2. unitは不変条件、状態遷移、失敗時の無副作用に絞る。調整値そのものを固定するtestは作らない。
3. 代表利用経路だけをE2Eで確認し、広い組み合わせは追加しない。
4. 独立したdiff reviewを一度行い、P0 / P1 findingを解消する。
5. 最終treeへ変更駆動validation DAGの必要gateを一度だけ実行する。
6. 品質gate後は意図した差分だけをstage・commitし、push、PR、merge、Issue close、顧客承認は従来どおり別の明示確認を受ける。

方向性確認は顧客の最終承認ではない。技術検証と最終受け入れも引き続き分離する。

## 暫定運用の上限

追加の自動化、profile、状態管理、専用templateはまだ作らない。まず3件の対話的な機能sliceで、試遊前の手戻り、安定化後に見つかった不具合、最終gateの再実行理由だけをIssueまたはPRへ簡潔に残す。3件後、または安全上必要なtestを遅らせたことで不具合を見逃した時点で、このoverrideを維持、修正、撤回するかを再検討する。
